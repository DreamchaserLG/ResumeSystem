# AI 分析提示词设计（当前阶段）

当前阶段只使用系统已有的 SQL 统计、岗位要求、简历原文证据和人工上传的附件。不引入向量数据库，也不把检索相似度解释为录用概率。

## 三类回答

| 场景 | 提示词 | 当前输入 | 回答重点 |
| --- | --- | --- | --- |
| 招聘运营查询 | app/prompts/analysis.md | 用户问题、统计窗口、授权范围、事实编号、异常、数据缺口 | 直接结论 → 岗位异常 → 口径限制 → 人工核对 |
| 岗位与简历核对 | app/prompts/match.md | 岗位技能、四态计数、同一申请的简历原文引文 | 逐项证据 → 待核实要求 → 面试核对 |
| 人工附件问答 | app/prompts/doc.md | 用户问题、附件名与已解析文本 | 直接回答 → 文件依据 → 缺失信息 |

模型只负责组织已提供的事实。统计数字必须来自事实块；简历引文必须逐字来自当前申请；缺少证据必须写成“待核实”，不能推断能力不足。姓名、性别、年龄、照片、家庭情况与住址不作为筛选依据。回复内容在交给页面前通过确定性校验，超出事实数字、无效事实编号、错误引用或匹配分数会触发修复或回退。

历史对话标题取首轮问题的核心短语；多轮问答记录在同一会话中。思考文本和最终回答分开展示，思考区可折叠。未配置模型密钥时，规则摘要也按相同结构展示，但不能替代模型对复杂附件的理解。

## 后续接入向量检索时的输入边界

向量库返回的每段证据应携带申请 ID、简历版本、原文位置、原文短句、岗位要求 ID 和授权范围。模型仍只消费通过权限检查与原文核验的片段；检索分数只用于召回，不直接作为候选人的能力分数。缺失、解析失败和明确不满足保持不同状态。待向量方案确定后，再扩展检索与重排，不改变这三类回答的事实边界。

## 参考实现

- [Job Application Assistant](https://github.com/Maxwell2048/job-application-assistant)：岗位要求拆解、逐项证据与引文验证；其文档也明确指出缺少证据不等于缺少能力。
- [Resume Job Matcher](https://github.com/sliday/resume-job-matcher)：岗位条件与简历片段对应、逐项解释；借鉴其“先明确要求，再引用原文”的组织方式。
- [AI Recruiting Resume Screener](https://github.com/vugarfamiloglu/ai-recruiting-resume-screener)：按岗位要求提供可审计证据，并避免让姓名、性别、年龄和照片影响判断。

以上借鉴的是设计原则，提示词及当前系统的数据契约均在本项目中重新编写。
